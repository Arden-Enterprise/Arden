### F01 new-account password guidance

- **Goal and path:** A person creating an account directly, through an invitation, or after Google verification sees the three password checks at the password field before submitting. The entry can be shown or hidden without submitting the form. The layout follows Arden's Living Archive authentication design at narrow and wide widths.
- **Scope:** New account registration, invitation registration and first-time Google password setup require 8 or more Unicode characters, one Unicode uppercase letter, and one punctuation or symbol character. Whitespace and accented lowercase letters alone do not count as special characters. The checklist shows exactly these three checks. Account setup, sign-in, password reset, and authenticated password change cap the typed password at 100 characters before the provider hashes it. Supabase may apply additional configured rules that Arden cannot evaluate locally; its account-setup failure remains non-enumerating.
- **Decision and provenance:** Accepted directly by the requesting user on 2026-11-07. Originator: requesting user (not identified in public project records). Accountable decision owner: requesting maintainer for this refinement; original owner of the earlier eight-character rule is not independently established by available public records. Record author: implementation contributor. Approval evidence: initial request for an inline checklist, an interim choice to display Arden's existing rules, then the user's explicit correction to show only 8 characters, uppercase and special character. After being told the API previously enforced only eight characters, the user explicitly selected mandatory form and API checks. This supersedes the interim 8–1024 display choice and the earlier new-account minimum-only rule.
- **Decision change and impact:** Previously, a new-account password with eight characters could reach Supabase without uppercase or punctuation, while new-account fields and API schemas capped input at 1024 characters. The accepted rule rejects passwords missing either new check before provider submission, including on the Google setup path, and removes that new-account-specific length cap. Existing credentials, sign-in, reset and change-password paths were unaffected by the composition checks; no migration or credential rewrite is required. On 2026-11-14 the requesting maintainer set one 100-character maximum on the typed password for account setup, sign-in, reset, and password change. That maximum replaces both the removed new-account cap and the previous 1024-character caps. The count is the password text before hashing. A stored password above 100 characters can no longer be typed into sign-in or password change; recovery can replace it with a password within the cap. Original-owner attribution remains incomplete. Team consultation before shared rollout is recommended and has not been recorded; the requesting maintainer approved this task's change directly.
- **Specification revision:** Arden main `9fa3d34a19a559318eff87b4487f2113e6ee5a49`, inspected 2026-11-07; implementation branch `feat/signup-password-guidance` starts at the same revision. The 2026-11-07 change applied the composition checks to new accounts. On 2026-11-14 the 100-character maximum was added to account setup, sign-in, reset, and password change.
- **Delivery evidence:** On 2026-11-07, focused tests passed for the domain checks (7), UI account paths (27) and API request contracts (51); root typecheck, test, remote-tool test and build also passed. Chrome showed the three checks, Show/Hide and no horizontal overflow at 1280, 375 and 320 px. The gated real-database API cases remain skipped (7 cases), and native interaction and live Supabase acceptance were not exercised. Integration and deployment remain pending.

### F01 24-hour session refinement

The requester chose a 24-hour limit for both ordinary and Google sign-in on 13 November 2026. This specification records that direct instruction; the requester is the decision owner for this refinement and the coding agent prepared the record. The limit is absolute from sign-in, including after provider token refresh. Arden signs a token-bound deadline in a server-only HttpOnly cookie, rejects missing/edited/expired deadlines and clears the session cookies. The same cookie set is stored in the desktop's encrypted main-process jar; the renderer receives only the deadline timestamp needed to clear an idle workspace. A fresh sign-in begins a new period. Existing sessions without the new marker require sign-in after rollout. F01-AC4 and F01-AC5 describe the password-guidance and link-only recovery refinements included in this bundle. This change does not provide a device/session list or change Supabase-owned Auth configuration.

### F02-AC2 batch invitation refinement (2026-11-07)

### F03-ARR Note order, in-place collection titles and Archive

- Spec revision/date: 1 / 2026-11-23. Refines F03-ORG and [ADR 0029](../decisions/0029-private-notes-organization-and-trash.md); owner-only access, trash retention and tombstones are unchanged.
- Originator and decision owner: requesting project maintainer. On 2026-11-23 the maintainer asked for these three features directly (relayed to the implementing session with two reference screenshots: the open collection page and a chat-app "Archived chats" page). Record author: coding agent. Approval evidence: that request. Linear: related to ARD-83; no separate issue recorded.
- Decision state: the three features are **accepted** (maintainer request). The details marked *agent choice* below were not discussed with the maintainer and are **proposed — confirmation needed**.
- Baseline: `origin/staging` d47ddc5 (Private Notes organization merged by #68); approved main read at 9fa3d34. Implementation branch `feat/private-notes-arrange-archive`; not committed, merged or deployed. API contract: [private notes organization API](../features/private-notes-organization/API.md#spec-f03-arr-order-and-archive). Migration `0064_private_notes_order_and_archive.sql`.

Scope:

1. **Order and drag and drop.** Notes in the sidebar tree can be dragged to reorder them inside a collection (or the root), dropped on a collection row (or its "No notes inside" line) to move into it, and dropped on the Private Notes header to move to the root. The order is stored on the server per container. Keyboard alternative: `···` on a note offers Move up and Move down (disabled at the ends) next to the existing Move to. Favorites keep their favorite-time order and are not draggable; collections stay sorted by title and are drop targets only. *Agent choices:* notes never placed by the owner sort first, newest first (this keeps today's "new note on top" behaviour); a drop on a collection and Move to put the note last; a reorder renumbers that container from 1; placement and archive changes do not change the note's "Saved" time.
2. **In-place collection title.** On a collection page, clicking (or pressing Enter/Space on) the title turns it into a field. Enter or leaving the field saves through the existing collection update; Escape cancels. An empty title is rejected: Enter keeps the field open with "A collection needs a title.", leaving the field restores the previous title. The sidebar row and the top-bar breadcrumb update from the same state. Rename in `···` still works.
3. **Archive.** `···` on a note (sidebar and note header) offers Archive, unavailable for never-saved notes and notes with unsaved edits. An archived note leaves the tree, Favorites, the collection page and the note list API, but keeps its content, favorite flag and collection reference. The account menu (bottom-left) gains **Archived** above Trash. The Archived view has a title and subtitle, a search box (title match), a sort control (Recently archived, Last edited, Title A–Z) and groups notes by the collection Unarchive returns them to (root last), each row with Unarchive and Delete. Unarchive returns the note to its collection while that collection is active, otherwise to the root, shown first there. Delete is the existing Move to trash (restorable for 30 days), not permanent deletion. *Agent choices:* trashing an archived note clears the archive flag, so Restore from Trash brings it back to the tree; trashing a collection leaves its archived notes archived; the view lists the 1,000 most recently archived notes and says so when more exist; archived notes cannot be favorited, moved or duplicated until unarchived; the owner can still read an archived note through its direct route (no UI path opens it). Design deviation from the reference: rows use the Island secondary/danger buttons, not pill buttons, per `DESIGN.md` ("no pill-everything").

Out of scope: dragging collections or reordering them manually, reordering Favorites, opening an archived note from the Archived view, archiving collections, a filter-by-collection control.

Collections, the collection page and the Private Notes root page no longer offer Import PDF.
- *Agent choices:* an empty note receives the text; a note that already has text keeps it and gets the PDF's text after a blank line (nothing is replaced). Pages are separated by a blank line; layout, images and tables are not kept. A note holds at most 100 KB of text including what is already there, so a long PDF keeps the whole pages that fit and the confirmation says how many of how many pages were imported; a full note refuses the import. Files over 25 MB, non-PDFs, password-protected or damaged PDFs and scans without a text layer get explicit errors and leave the note unchanged (no OCR).

### F03-SHR Share button and direct sharing

- Spec revision/date: 1 / 2026-11-26. Decision state: **accepted** ([ADR 0034](../decisions/0034-share-button-direct-share-and-private-pdf.md)); it relaxes product contract item 4 and F03 owner-only access for named recipients.
- Originator: requesting project maintainer (one-member sharing in Reports 1/3; the single Share button). Rules for review, cap and PDF: coding agent recommendation at the maintainer's request. Decision owner: requesting project maintainer. Record author: coding agent. Approval: maintainer, 2026-11-26, "Duyệt như đề xuất" after reviewing ADR 0034 as proposed, including the *agent choice* details. Team consultation: not recorded.
- Baseline `origin/staging` c62b2f6, `origin/main` 9fa3d34. Affected repository: Arden only (Core, UI, migrations); Arden-AI unchanged. Linear: not prioritized. Delivery: not started.

Goal: let an owner show a private note or private PDF item to named colleagues without review, and start every kind of sharing from one Share button, while keeping official knowledge on the reviewed path.

Scope:

1. **Share button** in the note/PDF header and `···`, opening a panel with **Share with people** and **Contribute to a department or the organization**. Contribute opens the existing contribution form (F07) unchanged.
2. **Share with people:** search active members of the organization by name or email, add several at once, see the current recipients and revoke one or all. Each recipient gets a separate view-only grant. The panel states "Not reviewed · view only · not an official document".
3. **Recipient view:** shared items appear in Home → Shared with me under a separate heading "Shared directly — not reviewed", apart from approved publications. The reader shows the owner's current saved content read-only with the label "Shared by ‹owner› — not reviewed". No edit, re-share, contribute, move, favorite or AI action.
4. **Limits:** individuals only (no department, group or Everyone); at most N active recipients per item, N set by the Organization Admin (default 10); the Organization Admin can disable direct sharing; near the cap the panel suggests Contribute.
5. **End of access:** owner revocation; owner moves the item to Trash (Restore does not re-share); purge; owner or recipient leaves the organization or becomes inactive. Archive keeps grants (*agent choice*).
6. **Audit and notice:** share/revoke audit events with actor, recipient, item id and time, without title or content; the recipient receives an in-app notice on share (new 0025 event type, no excerpt); revocation sends none.

Out of scope: recipient editing or comments, sharing collections, public links, people outside the organization, indexing for organization Ask Arden, recipient AI over shared items, "save a copy" for recipients.

Paths:

- Owner: open item → Share → Share with people → pick members → Share → recipients listed → Revoke one or Revoke all.
- Owner: Share → Contribute → existing contribution form → review (F07/F09).
- Recipient: notice or Home → Shared with me → open → read-only view; after revocation the item disappears and a stale link shows "You no longer have access".
- Admin: Organization settings → Direct sharing on/off and recipient cap.

### F03-FILE Private PDF items

- Spec revision/date: 1 / 2026-11-26. Decision state: **accepted** ([ADR 0034](../decisions/0034-share-button-direct-share-and-private-pdf.md)); it replaces the F03-PDF rule that the PDF file is never stored. Same provenance, baseline and delivery state as F03-SHR.

Goal: keep an original PDF in Private so that it can be organized, read, contributed and (after F03-SHR) shared without losing layout.

Scope:

1. **Upload PDF** on the Private page and on a collection page creates a PDF item next to notes. Maximum 5 MB. The server checks the file type and size; the file goes to protected private storage and is served only through owner-checked Core routes (`GET …/drafts/:id/pdf`, no-store), never through a public URL. *Implementation note:* this matches the existing shared PDF reader instead of the signed links first written here; the access boundary is unchanged.
2. The PDF's text is extracted for the title (PDF title, otherwise file name), search and the private AI side panel. A PDF without a text layer is accepted and labelled "No text found — AI is unavailable for this file" (no OCR).
3. The file cannot be edited. **Replace file** stores a new file as the item's live version under ADR 0031; a version sealed by contribution is kept; the replaced unsealed object is erased.
4. PDF items take part in collections, favorites, ordering, archive and the 30-day trash like notes; purge erases every stored file of the item.
5. **Contribute** creates a shared PDF draft through the existing PDF contribution path; a PDF without text is warned about because indexing needs text.
6. **Import PDF into a note** (F03-PDF) is unchanged for users who want editable text.

Out of scope: annotating PDFs, other file types, OCR, files over 5 MB.
