### F01 new-account password guidance

- **Goal and path:** A person creating an account directly, through an invitation, or after Google verification sees the three password checks at the password field before submitting. The entry can be shown or hidden without submitting the form. The layout follows Arden's Living Archive authentication design at narrow and wide widths.
- **Scope:** New account registration, invitation registration and first-time Google password setup require 8 or more Unicode characters, one Unicode uppercase letter, and one punctuation or symbol character. Whitespace and accented lowercase letters alone do not count as special characters. The checklist shows exactly these three checks. Account setup, sign-in, password reset, and authenticated password change cap the typed password at 100 characters before the provider hashes it. Supabase may apply additional configured rules that Arden cannot evaluate locally; its account-setup failure remains non-enumerating.
- **Decision and provenance:** Accepted directly by the requesting user on 2026-11-07. Originator: requesting user (not identified in public project records). Accountable decision owner: requesting maintainer for this refinement; original owner of the earlier eight-character rule is not independently established by available public records. Record author: implementation contributor. Approval evidence: initial request for an inline checklist, an interim choice to display Arden's existing rules, then the user's explicit correction to show only 8 characters, uppercase and special character. After being told the API previously enforced only eight characters, the user explicitly selected mandatory form and API checks. This supersedes the interim 8–1024 display choice and the earlier new-account minimum-only rule.
- **Decision change and impact:** Previously, a new-account password with eight characters could reach Supabase without uppercase or punctuation, while new-account fields and API schemas capped input at 1024 characters. The accepted rule rejects passwords missing either new check before provider submission, including on the Google setup path, and removes that new-account-specific length cap. Existing credentials, sign-in, reset and change-password paths were unaffected by the composition checks; no migration or credential rewrite is required. On 2026-11-14 the requesting maintainer set one 100-character maximum on the typed password for account setup, sign-in, reset, and password change. That maximum replaces both the removed new-account cap and the previous 1024-character caps. The count is the password text before hashing. A stored password above 100 characters can no longer be typed into sign-in or password change; recovery can replace it with a password within the cap. Original-owner attribution remains incomplete. Team consultation before shared rollout is recommended and has not been recorded; the requesting maintainer approved this task's change directly.
- **Specification revision:** Arden main `9fa3d34a19a559318eff87b4487f2113e6ee5a49`, inspected 2026-11-07; implementation branch `feat/signup-password-guidance` starts at the same revision. The 2026-11-07 change applied the composition checks to new accounts. On 2026-11-14 the 100-character maximum was added to account setup, sign-in, reset, and password change.
- **Delivery evidence:** On 2026-11-07, focused tests passed for the domain checks (7), UI account paths (27) and API request contracts (51); root typecheck, test, remote-tool test and build also passed. Chrome showed the three checks, Show/Hide and no horizontal overflow at 1280, 375 and 320 px. The gated real-database API cases remain skipped (7 cases), and native interaction and live Supabase acceptance were not exercised. Integration and deployment remain pending.

### F01 24-hour session refinement

The requester chose a 24-hour limit for both ordinary and Google sign-in on 13 November 2026. This specification records that direct instruction; the requester is the decision owner for this refinement and the coding agent prepared the record. The limit is absolute from sign-in, including after provider token refresh. Arden signs a token-bound deadline in a server-only HttpOnly cookie, rejects missing/edited/expired deadlines and clears the session cookies. The same cookie set is stored in the desktop's encrypted main-process jar; the renderer receives only the deadline timestamp needed to clear an idle workspace. A fresh sign-in begins a new period. Existing sessions without the new marker require sign-in after rollout. F01-AC4 and F01-AC5 describe the password-guidance and link-only recovery refinements included in this bundle. This change does not provide a device/session list or change Supabase-owned Auth configuration.

### F02-AC2 batch invitation refinement (2026-11-07)

Decision state: accepted for this scoped addition by the requesting user in the current Arden task. The requester originated the batch-invite request and is the accountable owner for this addition; the coding agent authored this record. The task request is the approval evidence; no private chat transcript or personal identity is copied here. Specification revision: 2026-11-07 on `feat/batch-invitations`, based on Arden main `9fa3d34a19a559318eff87b4487f2113e6ee5a49`. Integration and deployment remain pending.

An Organization Admin can enter one or up to 20 unique work email addresses in the existing Invitations form, separated by commas, semicolons or whitespace. The shared web/desktop UI previews normalized destinations before the admin presses Send. Duplicate entries are ignored; malformed addresses, existing members and active pending invitations are shown as skipped. A batch above the limit sends nothing. Eligible recipients are sent sequentially through the existing authenticated single-invitation API; each retains server authorization, hashed single-use token and audit behavior. An invalid or duplicate address does not prevent other eligible recipients from being invited.

The result names each unique address and distinguishes mail-server acceptance, local-only save, saved invitation with unconfirmed SMTP handoff, concurrent duplicate, server rejection, unconfirmed outcome and not-sent remainder. SMTP acceptance does not establish mailbox delivery; an unconfirmed handoff directs the admin to check provider status before resending. Authorization, configuration or uncertain failures stop further sends; the admin checks the refreshed list before retrying. Cancel clears an unsent draft. While sending, the form and administration tabs are disabled, workspace navigation and sign-out are held, and the client requests a browser exit warning. This refinement does not change acceptance or membership creation, add a new batch API endpoint, or send email without the admin's explicit form action. The maintainer's 16 November 2026 clarification identified a missing original invitation email, before account registration; live SMTP delivery remains unverified.

Evidence at this local revision: focused parser/delivery, rendered-form and shell-navigation tests cover deduplication, invalid/existing/pending entries, limit, cancellation, single-address compatibility, partial SMTP failure, authorization stop, uncertain network stop, and holding navigation/sign-out during sending. Root checks, visual review, live SMTP and real database paths are reported separately in the task handoff; this paragraph does not assert publication or deployment.

## F06 Installation administration

Scope: a dedicated, no-membership Arden System Admin account with least-privilege monitoring and a separately granted administrator-management capability. See [decision 0010](../decisions/0010-audiences-and-system-administration.md) and [implementation phases](../engineering/audience-system-admin-implementation.md).

Decision/provenance: the requesting user explicitly approved this refinement and implementation plan in the current Arden task on 2026-11-23. The requester originated and owns this refinement; exact identity is not included in this public record. The implementation contributor prepared the record. The approved refinement narrows the earlier decision's organization lifecycle/configuration access and combines the former broad System Admin grant API with the separately protected manager capability.

The System Console is shared by web and desktop. It provides an overview, searchable/filterable read-only organization list and details, knowledge repository status, AI usage/latency/citation/estimated cost, aggregate contributions by organization/department, minimal AI feedback and maintenance-case counts, anonymous quality signals, and sanitized Core/DB, Auth, Arden-AI and queue health. Date filters default to 30 days, offer 7/30/90/custom-day ranges up to 366 days, and pagination is capped at 50. Quality signals are at least two open cases, a publication unchanged for over 180 days, expiry, and duplicate hashes within one organization. Storage is referenced content bytes, not server disk use. No tenant content, original document IDs, individual names, prompts, answers, report text or provider error text may be returned. The console cannot mutate organizations or control services.

The API rechecks the active Arden account, current `INSTANCE_ADMIN` grant and absence of every organization membership on each call; `MANAGE_SYSTEM_ADMINS` is required for administrator list/grant/revoke/capability APIs. New grants are monitors by default. A one-time operator bootstrap chooses the first manager. Profile registration from a verified Auth session creates no organization membership or privilege. The no-workspace onboarding screen allows a signed-in account to continue without creating an organization while awaiting separately assigned access. Database and API paths serialize membership creation against System Admin grant/activation. The last active administrator and last active manager cannot be removed. Changes to manager capability are audited.
