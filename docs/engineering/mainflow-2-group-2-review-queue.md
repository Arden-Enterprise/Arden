# Mainflow 2 — Group 2, function 1: listAssignedReviews

> Historical slice note: this records the earlier pure-function-only state. For the current server routes and migration path, see [mainflow-2-workflow.md](./mainflow-2-workflow.md). In particular, the ARD-29 worktree mentioned below was removed and is not a dependency of the current branch.

This slice adds review-queue authorization and a decision planner in `apps/api/src/knowledge/`. They are deliberately **not** HTTP endpoints or a claim that real submissions can be reviewed yet.

`listAssignedReviews()` receives an active actor, the server's current time, and candidates hydrated from current database state. For each pending submission, it checks all of that reviewer's live grants through `canRespondToSubmission()`. A candidate appears only if at least one grant matches the organization, responsible department, optional team/project attributes, classification and policy version. Self-review, an inactive membership, expired/revoked grants, completed submissions and invalid queue records fail closed. Authorized results are deduplicated and ordered newest first. The function returns limited queue metadata, not private source content or storage URIs. An unenforceable proposed audience keeps the submission in the queue with `approvalBlocked: true`: the reviewer may request revision or reject, but cannot approve it.

The candidate submission, reviewer grants, effective policy version and audience-enforceability result are **server-resolved authorization facts**; an API must never accept them from a client. Before a production route is enabled, Group 1 still needs shared-draft update and immutable submission creation; the DB model needs reviewer-grant persistence, frozen metadata/audience, and narrow RLS/read policies. The route must check authorization again for detail and at decision time, since a grant may be revoked after queue listing. Final approval must still atomically create system publication for the exact approved snapshot; this slice adds no decision or publish route.

`planReviewDecision()` rechecks the frozen snapshot ID/hash and current reviewer authority. Request Revision and Reject require a nonempty reason and never produce publication intent, even when the proposed audience is invalid. Approval requires an enforceable audience and an explicitly resolved single-reviewer policy; an unsupported/multi-step policy fails closed until its evaluator is implemented. The only approval output is an `APPROVE_AND_PUBLISH_ATOMICALLY` plan. It is **not** a successful publication: the future route must lock the submission, rehydrate all facts, and commit review decision, immutable publication, current pointer and audit evidence in one database transaction. A second concurrent decision or failed write must not leave partial publication.

`canReadPublication()` also requires a current publication inside its validity interval. Readership needs either active organization membership for an Organization-only `ALL_MEMBERS` audience or a live exact-scope assignment to an active audience role. A read route must fetch those facts from the database for every request and fetch protected content only after this policy passes.

The separate ARD-29 `packages/db` worktree is still uncommitted and follows a different migration ledger than this branch's `apps/api/migrations`. Per the branch owner's direction, do not introduce another competing review/publication schema here. Reconcile one canonical migration path after ARD-29 is ready; only then wire submit, queue/detail, decision, automatic publication and authorized read endpoints and run real PostgreSQL/RLS and concurrent-decision tests.

Verify with `pnpm --filter @arden/api test`, `pnpm --filter @arden/api typecheck`, and `pnpm --filter @arden/api build`. These are unit/build checks only; no migrated PostgreSQL or Coolify slot is modified by this slice.
