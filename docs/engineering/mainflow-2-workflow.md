# Mainflow 2 — current workflow and verification boundary

This is the current Flow 2 contract. Earlier `mainflow-2-group-1-create.md` and `mainflow-2-group-2-review-queue.md` document incremental slices; their statements about absent routes and the ARD-29 worktree are historical, not the current branch state.

## Authoring

There are two creation paths. `POST /api/v1/organizations/:organizationId/knowledge/drafts/new` starts a new text draft; `POST /api/v1/organizations/:organizationId/knowledge/drafts` makes a separate **Contribute copy** of one saved private-note version. Both require an authenticated, active organization member and a UUID `Idempotency-Key`. Only the private-note owner may contribute that note. The private original and its protected object remain unchanged.

Each shared draft has immutable content versions. `GET /knowledge/drafts` lists only the actor's drafts, `GET /knowledge/drafts/:id` reopens one, and `PATCH /knowledge/drafts/:id` requires `If-Match: "<current version>"`. Editing writes a new version; it never mutates the previous one. The author supplies title, target scope, optional team/project tags and active audiences; the server derives the responsible department from the author's active primary department. `GET /knowledge/options` provides audiences, the primary department and whether an active Organization reviewer exists. The working draft remains editable while a frozen submission is pending.

`POST /knowledge/drafts/:id/submit` requires `If-Match` and an idempotency key. Submission freezes the exact current version, title, legacy classification value, responsible department, scope, tags, audience IDs, review rule, content URI and hash. A draft needs the author's active primary department, target scope and at least one valid audience. The managed organization audience is valid only for Organization scope.

## Review and publication

Org Admin creates a `reviewer_grant` through Administration or `POST /knowledge/reviewer-grants`. A grant has disjoint `DEPARTMENT` or `ORGANIZATION` scope, optional team/project tags and a validity interval. Department scope requires one active department; Organization scope has no department. New grants store `STANDARD` without exposing levels in the product. A new organization-wide snapshot requires an Organization grant; department and group-only snapshots require a Department grant for the responsible department. Existing `LEGACY` organization-wide submissions additionally accept the old responsible-department Specialist/Senior rule, and legacy classification checks remain. Organization Admin is the final organization authority and may review any submission, including their own; self-approval is explicitly audited. This authority does not independently grant published-content readership. Grants can be deactivated; each queue, detail and decision request rechecks current membership and grant status.

`GET /knowledge/reviews` returns only pending submissions within the ordinary reviewer's current grants; ordinary self-review is excluded. Organization Admin sees every pending organization submission. The queue returns metadata, not protected text. `GET /knowledge/reviews/:submissionId` reauthorizes, loads the exact immutable submitted text, and reauthorizes again before responding. If proposed audience roles are no longer enforceable, the queue marks `approvalBlocked`: rejection remains possible, approval does not.

`POST /knowledge/reviews/:submissionId/decisions` requires a UUID `Idempotency-Key`, the expected snapshot-version ID and content hash. Review has only Approve and Reject; Reject requires a reason and never publishes. Approval locks the submission, rechecks authority/audience, records the immutable decision/audit and moves the exact snapshot to `PREPARING`. It does not replace the current-publication pointer. A later complete index generation atomically activates the candidate. The author may edit the working draft throughout review and can submit a new snapshot after the open candidate closes.

`GET /knowledge/published` and `GET /knowledge/published/:id` expose only the current active publication. Custom/default audiences require a live assignment in the exact current scope; Organization-only `ALL_MEMBERS` requires active organization membership and no assignment. The detail endpoint rechecks authorization after reading protected text. Approval does not automatically make the reviewer or Org Admin a reader unless an independent audience rule grants access. Only current approved/published versions are eligible for future Search/AI use; Search/AI implementation is outside Flow 2.

## Migration and deployment gate

This branch uses one migration ledger, `apps/api/migrations`, including `0009_mainflow_2_authoring.sql`, `0010_mainflow_2_submission_review.sql`, the forward fix `0016_fix_flow2_cross_actor_validation.sql`, and `0022_organization_reviewer_grants.sql`. Migration 0022 adds grant scope and frozen `review_rule`; its legacy-signature SQL eligibility function is deliberately broader than the disjoint TypeScript policy until schema contraction. The deleted ARD-29 worktree is not a dependency. The UI separates authenticated server records from session-only samples; Electron's main process allowlists the live routes and keeps tokens outside the renderer.

The opt-in disposable PostgreSQL integration suite was not run in this checkout because `ARDEN_TEST_DATABASE_URL` was unavailable. Migration 0016 and the exact cross-member approve/publish transaction were instead applied inside one rollback-only transaction on the `dev-3` PostgreSQL database under `arden_runtime`; the decision, both audit events, published version, current pointer, and deferred constraints completed before rollback. This is targeted regression evidence, not a substitute for clean-install, concurrency, and full actor-boundary testing on a disposable `arden_test_*` database. Do not use a shared Coolify Supabase instance as a disposable test database. On 2026-10-16 migration 0016 was applied and recorded in the `dev-3` hosted ledger with the reviewed migration-owner role; post-commit object checks and the API readiness check succeeded. Staging and production were not changed.
